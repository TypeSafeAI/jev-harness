# Routing v5: clarify the desired outcome

Two frozen, single-attempt routing batches reached every expected outcome on
the existing synthetic suite: 57/57 in each batch, with no malformed
probability distributions or retries. These are repeated development cases,
not held-out calibration. Delivered-answer quality requires the separate full
CLI comparison; the routing-only runs do not measure it.

## Change and frozen setup

Candidate source:
[`fda2774667872968e1ef48271faa040e435ffdfc`](https://github.com/TypeSafeAI/jev-harness/commit/fda2774667872968e1ef48271faa040e435ffdfc).
The source is signed and passed 268 offline tests, typecheck, production build,
secret checks, and independent compatibility review before measurement.

V5 changes only the generic clarification wording from v4: a named target is
not a specified outcome; materially different possible outcomes require
clarification; a vague improvement request does not establish a concrete edit.
The model, catalog, tasks, labels, mocks, policy, confidence floor, probability
validation, prerequisites and fixture host remain fixed. V1–v4 request bodies
remain available unchanged for replay. Arena setup 6 separates new runs from
older cohorts.

This follows the [v4 wire diagnostic and bounded recovery experiment](2026-09-26-distribution-diagnostic.md).
The single-attempt control reached 53/57. Maximum-three-attempt recovery reached
57/57 then 56/57, with additional provider usage and one exhausted case. Recovery
was not integrated. V5 asks a clearer question while retaining the same strict
evidence contract; it does not repair, normalize or tolerate malformed output.

## Routing-only measurements

Each batch uses the same 19 task/catalog combinations three times. The
[manual runner](runs/2026-09-26-routing-v5-diagnostic.mts) pins the candidate
commit, allows exactly one attempt per case, bounds each response, checks source
and runner hashes before/after, and joins evaluation labels after provider work.
No proposer or CLI is called in these batches.

All 39 clear-task cases in each batch selected an acceptable tool under the
frozen labels. All 18 ambiguous cases in each batch requested clarification.
All probability distributions met the existing sum tolerance. No invalid
response was accepted, and no confidence or probability threshold changed.

The longer instruction added 1,311 provider-reported input tokens per batch
relative to the v4 single-attempt diagnostic: 23 tokens per request. Output
usage was unchanged at 7,185 tokens per batch. These routing-only totals do not
establish total harness cost, monetary savings or execution-speed improvements.

## Limits and next gate

The existing cases influenced development, so this is adaptive tuning. Repeated
runs test variability on these cases, not independent task coverage. Zero
malformed responses in these batches does not guarantee future validity or
model reliability. Correct clarification is an expected routing outcome, not
a delivered answer or authorization.

The candidate still needs the full paired CLI comparison with fixture host
revision 1 and the existing frozen blinded-output rubric before a final
integration claim. Retain all baseline and routed outputs, failures, usage and
assessment provenance. Proposal-review wording and verdicts remain unchanged;
its [200/200 observed result](../calibration/2026-09-25-question-set-v4.md) is
separate evidence and not a routing score.
